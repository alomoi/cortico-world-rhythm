# 睡眠表现与「被吵醒」状态 · 设计草案

> 状态：**草案，待主人确认**。前置：P0/P1 已完成（时段、上限、退避）。
> 目标：形象在睡眠时段真的去睡；被打扰后过一会儿自己睡回去；并把「被吵醒几次」共享给别的软件。

---

## 1. 先说清楚能做到什么、做不到什么

| 想法 | 可行性 | 说明 |
|---|---|---|
| 插件代码直接让形象睡着 | ❌ | World 之间没有互相调用工具的通道；桌宠窗口只连它自己的 panel/stream，插件推不过去 |
| 让 Coo 用 `pet_act` 睡着 | ✅ | 桌宠词表里有 `sleep`（「坐着打盹」，`lasting: true` → 保持到下一个动作），模型调 `pet_act(["sleep"])` 就能真睡 |
| 用户消息打断睡眠 | ✅ 本来就不会拦 | 插件从不拦人侧事件；桌宠身体对戳/摸也有自己的反射（睡着被戳会吓醒，宿主行为） |
| 被吵醒后 10–30 分钟睡回去 | ✅（模型中介） | 安静够久就再投一条「可以继续睡」的提示，让 Coo 自己调 `pet_act sleep` |
| 记录「被打扰几次」并共享 | ✅ | 睡眠时段内的人侧事件可数；落盘 + 归档事件 + 一份公开状态文件 |

**关键限制**：睡眠提示是「建议」，不是命令——Coo 可能不理；桌宠窗口没开时 `pet_act` 会回执失败；它也可能自主醒来（宿主会自己打盹/醒来）。
所以文案一律写「如果你愿意」，不承诺「一定睡着」。

---

## 2. 行为设计

### 2.1 入睡提示（每个睡眠时段最多一次）

进入睡眠时段时（`sleepWindow` 生效的那一刻）：

- 若 `sleepHint` 打开、且主循环空闲 → 投一条 internal 提示，正文大意：
  > [23:00] [作息] 到睡觉时间了，现在没人找你。想睡的话，可以用 pet_act 的 sleep 动作躺下（它会保持到你下一次动作）；不想睡也可以做自己的事，或者结束这一轮。
- 不计入 `dailyCap`、不算「本轮叫醒」，但**会**记一次 `sleepHints` 日志与状态。

> 为什么不在睡眠时段完全静默：那样形象永远不会「去睡」，只能靠它自己打盹。一次提示换一夜安静，值得。

### 2.2 被打扰与回睡

- 睡眠时段内出现**人侧事件**（和 P0 同一套渠道判定）：
  - 第一次 → `wokeCount += 1`，记 `lastWokeAt` / `lastWokeBy`（渠道类型，如 `clawbridge.message`）；
  - 之后的连续互动**不重复计数**（一次打扰算一次，不按消息条数刷）。
- 从最后一次人侧事件起安静满 `wakeBackToSleepMinutes`（缺省 20，允许 10–120）：
  - 若还在睡眠时段内、主循环空闲 → 投一条「可以继续睡」的提示（每个睡醒周期最多一次）；
  - 下一个人侧事件到来时再 `wokeCount += 1`。
- 睡眠时段结束（早上）→ 该夜结束，`wokeCount` 归零进「昨晚统计」；`dailyCap` 不受影响。

### 2.3 与现有规则的关系

- 睡眠时段内**仍然不主动叫醒**（P1 的规则不变）；入睡/回睡提示是例外，单独计数、单独开关。
- 回睡提示不计入 `dailyCap`，否则夜里被吵几次就会把白天额度吃光。
- 提示同样走 `pushDeferred` + `render` 复查：排队期间人又回来了、或已经过了睡眠时段，就作废。
- 队列里若还有入睡提示没投递，用户先说话了 → 这条入睡提示自然作废（`render` 检查到新人侧事件）。

## 3. 「被吵醒」状态怎么共享出去

三条通道，按使用方选：

### 3.1 公开状态文件（主通道）

`<dataDir>/rhythm/status.json`，由插件在状态变化时原子重写（不影响内部 `state.json`）：

```json
{
  "version": 1,
  "generatedAt": "2026-11-02T23:41:00+08:00",
  "sleep": {
    "active": true,
    "window": "22:00-08:00",
    "endsAt": "08:00",
    "wokeCount": 2,
    "lastWokeAt": "2026-11-02T23:38:12+08:00",
    "lastWokeBy": "clawbridge.message",
    "hintSent": true,
    "backToSleepSent": false
  },
  "today": { "nudges": 3, "cap": 12 }
}
```

- 只写这些非敏感事实，不含 token、完整用户 id、本机路径。
- 其他软件（同进程的 World、外部脚本）直接读文件即可；结构版本化，字段只增不减。
- 微信桥要「给桌宠提示被吵醒」时，可以读这个文件，把 `wokeCount` 拼进消息上下文。

### 3.2 归档事件（同进程内可选）

每次打扰推一条 `rhythm.woke`，`deliver: false`（只入库、不进模型上下文）：

```
type: rhythm.woke, origin: internal, meta: { wokeCount, by: 'clawbridge.message' }
```

同进程的其他 World 可以用 `store.range({ type?… })` 读到（注意 `range` 不支持按 type 过滤，得自己筛）。
好处：事件库本来就有时间轴；坏处：会占事件库空间，且模型看不见（除非被投递）。

### 3.3 不要做的

- 不写进 `config.json`（那是配置，不是状态）。
- 不把打扰内容、消息正文写进任何共享文件。

## 4. 新增配置（2 个）

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `sleepHint` | boolean | true | 入睡与回睡时投一条提示，让 Coo 自己决定用 `pet_act sleep` 躺下 |
| `wakeBackToSleepMinutes` | integer | 20 | 被吵醒后安静多久再提示它回去睡（10–120，随机抖动 ±5 分钟） |

> 若嫌费 token，把 `sleepHint` 关掉：行为回到 P1（夜里完全静默），但形象不会主动去睡。

---

## 5. 状态文件（内部）

`rhythm/state.json` 增加（内部用，不对外承诺）：

```json
{
  "sleepSession": {
    "nightKey": "2026-11-02",
    "wokeCount": 2,
    "lastWokeAt": "...",
    "lastHintAt": "...",
    "backToSleepAt": "..."
  }
}
```

跨夜（睡眠窗口跨午夜）用「睡眠时段开始的日期」作为 `nightKey`，避免 23:59 → 00:01 被当成两晚。

---

## 6. 日志

- `作息:进入睡眠时段`（已有）加 `hint: sent|skipped`
- `作息:入睡提示`（轮次、phase）
- `作息:被吵醒`（`by`、`wokeCount`）
- `作息:回睡提示`（quietMinutes）
- `作息:睡眠时段结束`（`wokeCount`、`hints`）

## 7. 测试（仍用假宿主 + 假时钟）

- 进入睡眠时段且 `sleepHint` 开 → 恰好一条提示；关 → 没有。
- 睡眠内人侧事件 → `wokeCount` 1；连续多条第 2 条不重复计数。
- 安静满 20 分钟 → 回睡提示一条；再说话 → `wokeCount` 2。
- 回睡提示排队期间人回来 → 作废（`render` 返回 null）。
- 跨午夜睡眠：`nightKey` 不变；早上出窗口 → 归零。
- 提示不计入 `dailyCap`：把 `dailyCap=1`，白天用满后夜里仍能发入睡提示。
- `status.json` 内容随状态更新（active/endsAt/wokeCount/lastWokeBy）。
- 睡眠时段外不产生入睡/回睡提示。

---

## 8. 风险与边界

- **不能保证睡着**：提示只是建议；模型可能拒绝或调错动作。`pet_act` 在桌宠窗口没连上时直接失败（回执里能看到）。
- **形象醒着但气泡在说话**：`sleep` 是 lasting 动作，用户发消息时身体可能还保持睡姿 → 提示文案里建议 Coo 先用 `pet_act(["stand"])` 再说话。
- **会多花 token**：默认一夜最多 1 次入睡 + 每晚最多 3 次回睡（封顶），约 4 次模型调用；不喜欢的可以关掉。
- **不碰桌宠其他行为**：不调 `pet_quiet`、不改设置、不隐藏窗口；只建议动作。
- 别人（clawbridge）读文件需要一个约定路径；建议把路径与字段写进 `docs/`，并在 clawbridge 侧另开一个小改动（本次不做）。
